
# J2ME LLM v0.3 覆盖更新与恢复指南

本指南说明从 v0.1 / v0.2 覆盖更新到 v0.3 时 RMS 如何保留与迁移、应用如何用主备记录自恢复，以及怎样用 `.j2cfg` 做升级前备份。v0.3 沿用 v0.2 引入的 profile、会话和 `.j2cfg v2` 数据格式，只新增独立的界面语言偏好库。先看结论：

> 升级时保留相同的 `MIDlet-Name` 与 `MIDlet-Vendor`，选择安装器的“更新/替换”操作；**不要卸载旧版后再安装 v0.3**。

Java ME 的 RMS 属于 MIDlet suite。卸载 suite 通常会删除其 RecordStore，之后安装同名软件也不能恢复这些记录。Oracle 的 `RecordStore` 说明也明确指出，suite 被移除时其 record stores 会被删除；参见 [Oracle Java ME RMS RecordStore](https://docs.oracle.com/javame/config/cldc/ref-impl/midp2.0/jsr118/javax/microedition/rms/RecordStore.html)。

## 1. 版本身份与覆盖更新条件

v0.3 发布包应保持：

- `MIDlet-Name: J2ME LLM`
- `MIDlet-Vendor: Chihoko`
- 主类 `com.chihoko.j2mellm.LlmMidlet`
- `MIDlet-Version: 0.3.0`

不同厂商安装器对 suite 身份、签名、安装来源 URL 和版本号的判断可能不同。Sony Ericsson 等设备若显示“更新现有应用”或“替换”，才表示走覆盖更新路径；若只显示并列安装，先取消并检查 JAD 的 Name、Vendor、版本和签名，不要冒险继续。

若旧版曾签名，v0.3 通常还需要同一证书/签名身份。未签名与已签名包互换也可能被设备视为不同 suite。

## 2. 升级前备份

### 2.1 v0.2 或 v0.3 已可运行时

在应用中导出 `J2ME-LLM-backup-<毫秒时间戳>.j2cfg`，再把文件复制到可信电脑或离线存储。导出需要 JSR-75 FileConnection 写权限。文件名每次不同；若同名目标已经存在，应用会取消导出，不覆盖旧文件。

备份内容包括：

- 活动档案；
- OpenAI、DeepSeek、Kimi、自定义四档案的端点、Key、模型和行为设置；
- 思考协议、思考模式、强度、多模态和上下文设置。

备份不包括：

- 聊天记录；
- 模型列表缓存与缓存时间；
- 图片原始字节或预览；
- RMS 主备记录本身。

`.j2cfg` 中 API Key 是明文语义数据。Base64 只用于包装，CRC-32 只检测损坏；二者都不提供机密性或来源认证。升级成功并确认可恢复后，删除不再需要的临时文件。

导出采用“同目录临时文件 → 回读逐字节校验 → 改名”的顺序。最终目标从不执行 `truncate` 或删除：目标在开始或改名前已经存在都会报错，旧备份保持不变。改名后的最终文件还会再回读一次；若设备文件系统无法保证同目录改名，应用报告失败并保留可诊断文件，而不会牺牲已有备份。

### 2.2 仍在 v0.1 时

v0.1 没有 `.j2cfg` 导出功能。若安装器确实支持覆盖更新，v0.3 会读取旧 RMS；仍建议在升级前手工记录聊天端点、模型和系统提示词，并确认上游 Key 可以重新签发。不要为了“干净安装”而先卸载。

## 3. v0.1 到 v0.3 的自动迁移路径

首次启动 v0.3 时，仍使用 v0.2 引入的 v2 存储迁移路径：

1. 尝试打开 v0.2 配置库 `J2MELLM_PROFILES`。
2. 若该库存在且有可校验的 v0.2 记录，直接加载，不重复读取旧配置。
3. 若该库完全不存在，创建四个默认档案，再只读打开旧库 `J2MELLM_CFG` 的记录 1。
4. 旧记录格式有效时，把端点、API Key、模型、系统提示词、流式设置和上下文消息数迁入 `custom` 档案，名称设为“自定义（旧配置）”，并把它设为活动档案。
5. 模型目录端点由旧聊天端点推导；旧模型名也加入该档案的模型缓存。
6. 保存新的 v0.2 主备记录。旧 `J2MELLM_CFG` **不会被删除**。

聊天历史独立迁移：

1. v0.2 的每个档案使用单独的 `J2CHAT_<profile-id>` RecordStore。
2. 第一次加载 `custom` 历史且 `J2CHAT_custom` 不存在时，读取旧 `J2MELLM_CHAT`。
3. 旧历史非空时，把它写成 v0.2 的 `J2CHAT_custom` 主备记录并返回给界面。
4. 旧 `J2MELLM_CHAT` 不会在迁移后主动删除。

因此 v0.1 的单配置、单历史自然落到 v0.3 的“自定义（旧配置）”档案；其他三个官方档案保持发布默认值。若从 v0.2 更新，现有 v2 档案和分档案历史会直接加载，不做二次迁移。

### 3.1 为什么旧库不立即删除

迁移是“先读旧数据、成功写新数据、保留旧数据”的保守流程。这样在首次写入中断、设备突然断电或用户需要回查时，旧数据仍可能存在。代价是短期占用少量 RMS 空间。

不要把保留旧库理解成可以安全降级：v0.1 不认识 v0.2 的多档案设置，降级后修改旧配置也不会同步回 v0.2。

## 4. v0.3 沿用的 RMS 布局

| 数据 | RecordStore | 记录布局 | 校验与恢复 |
| --- | --- | --- | --- |
| 四档案与活动档案 | `J2MELLM_PROFILES` | 1 为主记录，2 为备份 | v2 magic、格式版本、CRC-32；主记录坏时读备份并修复主记录 |
| OpenAI 历史 | `J2CHAT_openai` | 1 主、2 备 | v2 magic、profile id、CRC-32 |
| DeepSeek 历史 | `J2CHAT_deepseek` | 1 主、2 备 | 同上 |
| Kimi 历史 | `J2CHAT_kimi` | 1 主、2 备 | 同上 |
| 自定义历史 | `J2CHAT_custom` | 1 主、2 备 | 同上，并承担 v0.1 历史迁移 |
| 界面语言偏好 | `J2MELLM_UI_PREFS` | 记录 1 | v0.3 新增；独立于档案和聊天，缺失或无效时回到“跟随系统” |
| v0.1 单配置 | `J2MELLM_CFG` | 记录 1 | 只读迁移来源，不自动删除 |
| v0.1 单历史 | `J2MELLM_CHAT` | 记录 1 | 只读迁移来源，不自动删除 |

保存 v0.3 配置或历史时：

1. 先编码新值并计算 CRC；
2. 若旧主记录仍有效，把旧主记录复制到备份记录；
3. 再写入新主记录；
4. 新建库首次写入时，主、备都写入同一个有效快照。

这不是事务型数据库，但能覆盖常见的“最新一次写入损坏”情形。备份是上一份有效快照，不一定包含刚刚修改但未成功落盘的设置。

## 5. 自动恢复行为

### 5.1 配置主记录损坏

若 `J2MELLM_PROFILES` 记录 1 的格式、版本或 CRC 无效，而记录 2 有效，应用加载记录 2，标记“从备份恢复”，并尝试用该内容修复记录 1。用户可能丢失最近一次保存，但此前有效档案仍可用。

### 5.2 配置主备都损坏

若 v2 配置库存在但主备都无法解码，应用使用安全的四档案默认值并标记存储损坏。此时不会把同名旧 v0.1 配置自动覆盖进来，因为“已有 v2 库”与“从未迁移”是不同状态。优先导入 `.j2cfg`，或根据升级前记录手工恢复。

### 5.3 某档案历史主记录损坏

若该档案历史的主记录无效而备份有效，应用加载备份，标记恢复状态并尝试修复主记录。其他档案历史不受影响。

### 5.4 某档案历史主备都损坏

该档案显示空历史；其他档案、Key 与设置仍应正常。聊天历史不在 `.j2cfg` 中，因此无法由配置包恢复。

### 5.5 `.j2cfg` 损坏或不兼容

导入顺序是：文件大小 → 外层 JSON → 格式名和版本 → Base64 → payload 大小 → CRC-32 → payload JSON → 档案数量和字段范围。任一步失败都应拒绝整包，不把半解析数据写入 RMS。

当前格式名为 `j2me-llm-config`，版本为 2；文件最大 32 KiB，payload 最大 24 KiB，最多 8 个档案。v0.3 用户界面使用四个固定档案。界面语言不写入 `.j2cfg`。

## 6. 推荐覆盖更新步骤

1. 给手机充足电，退出正在进行的模型请求。
2. 若正在运行 v0.2 或 v0.3 的预览版，先导出 `.j2cfg`；v0.1 用户至少手记端点和模型。
3. 保留旧 JAR/JAD 的副本，但不要卸载手机上的 suite。
4. 把 v0.3 JAR/JAD 放到与旧版相同的安装位置或通过同一发布 URL 更新。
5. 核对 JAD：Name、Vendor 不变，Version 为 `0.3.0`，JAR size 与文件匹配。
6. 在手机安装器中选择“更新/替换”，拒绝“删除旧应用后重装”。
7. 首次启动后检查活动档案是否为“自定义（旧配置）”，端点、模型、系统提示词与旧版一致。
8. 检查自定义档案的旧聊天是否出现，再分别打开其他三档案确认其历史为空且 Key 独立。
9. 做一次短文本测试；需要时再测试流式、思考和图片。
10. 切换一次界面语言并重启，确认偏好保持；随后立即导出一份 v0.3 `.j2cfg`，在离线生成器中做“载入备份检查”。

## 7. 从 `.j2cfg` 恢复

1. 在可信设备确认文件名以 `.j2cfg` 结尾，大小不超过 32 KiB。
2. 可先用 `provisioner/index.html` 的“载入备份检查”验证版本、Base64、CRC 和 JSON。
3. 通过蓝牙、存储卡或数据线把文件放到 Java 手机可读取的位置。
4. 在应用中选择导入并定位文件；允许一次文件读取权限。
5. 导入成功后检查当前档案、端点、模型、思考协议和多模态状态。
6. 对每个含 Key 的档案做最小请求验证；不要一开始就发送敏感提示词或大图片。
7. 在导入成功提示中选择删除手机上的明文配置包，并清理安卓下载目录、蓝牙收件箱和中转设备上的副本。

导入用于替换/更新档案配置，不会清理其他档案聊天。包中出现的档案替换对应槽位；包中没有出现的档案会保留原有 Key、端点、模型、开关和缓存。包未指定活动档案时继续使用导入前的活动档案。若希望彻底清空某档案聊天，应在应用中切到该档案后单独清空。

## 8. 失败时不要做什么

- 不要反复卸载、重装并期待 RMS 自动回来；
- 不要用文件管理器删除不认识的 RMS/应用数据文件；
- 不要把 `.j2cfg` 上传到在线“修复 JSON”网站；
- 不要为了绕过 TLS 把真实上游 Key 放在公网 HTTP 请求里；
- 不要在新配置库已经损坏时依赖自动重复迁移旧库，应该使用备份或手工恢复。

## 11. 设计边界

主备记录降低单次写坏的风险，但不能防止闪存整体损坏、用户卸载 suite、厂商安装器清除数据或恶意软件读取 RMS；CRC 也不是密码学签名。重要 Key 应能随时撤销，重要配置应保有一份受控的离线 `.j2cfg`，聊天记录则不应被视作永久档案。

本文按 2026-07-25 的 v0.3 实现与 Java ME RMS 行为编写；profile、会话和 `.j2cfg` 的格式版本仍为 v2。

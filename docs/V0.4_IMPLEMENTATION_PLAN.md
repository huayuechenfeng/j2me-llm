# v0.4 实施方案

状态：核心实现完成，等待模拟器交互回归与目标真机验证。

## 1. 目标与范围

v0.4 的目标不是继续增加服务商数量，而是让客户端具备完整聊天产品应有的基本操作，同时把联网搜索、长上下文和高性能设备能力做成可控、可回退的功能。

本版本包含：

- 多对话：新建、切换、重命名、删除、自动标题和摘要。
- 消息操作：编辑用户消息并重新发送、重新生成回答、错误回答重试。
- 联网搜索：全局配置、搜索并发送、预设适配、结果持久化和提示词注入。
- 资源限制：兼容、推荐、自定义三档上下文预算。
- 图片限制：兼容、高性能、自定义三档输入、像素和返回大小预算。
- v0.2/v0.3 历史迁移、主副索引恢复和逐消息 CRC。
- 网关搜索代理，供 TLS 能力不足的真机使用。

暂不包含：对话分支树可视化、跨设备同步、自动后台搜索、网页全文抓取、向量数据库和工具调用协议。

## 2. 已实现架构

### 2.1 对话存储

- 全局索引：`J2MELLM_CHATS`，主记录 + 恢复副本。
- 每个对话：独立 `J2C_<conversationId>` RMS。
- 每条消息：独立记录、CRC-32、长文本使用 32 位 UTF-8 长度，不受 `DataOutput.writeUTF` 的 65,535 字节限制。
- 对话保存采用“先写新消息记录，再切换索引”的方式；主索引和副索引仍引用的记录不会被清理。
- 首次启动 v0.4 时扫描旧 `J2CHAT_<profileId>`，每个非空旧历史迁移为一个新对话；旧 RMS 不删除。

编辑和重新生成采用线性分支语义：保留目标用户消息之前的内容，删除该消息及之后的旧分支，再提交新消息。这样不需要在低内存设备上维护分支树。

### 2.2 搜索链路

流程：

1. 用户在编辑器选择“搜索并发送”。
2. 搜索适配器返回统一的 `title / url / snippet`。
3. 客户端按结果数和字符预算裁剪、去重。
4. `SearchBundle` 随触发它的用户消息持久化。
5. 请求写入器把来源放在明确的 `UNTRUSTED REFERENCE TEXT` 区块，要求模型忽略搜索文本中的指令。
6. 原始问题仍是消息正文；搜索失败不会悄悄退化为普通发送。

| 预设 | 密钥 | 默认调用 |
| --- | --- | --- |
| DuckDuckGo + Wikipedia | 无 | DuckDuckGo Instant Answer，不足时补充中/英文 Wikipedia OpenSearch |
| 公共 SearXNG | 无 | 可编辑公共实例；仅作参考，实例可能限流或停机 |
| Brave | 需要 | `X-Subscription-Token` |
| Tavily | 需要 | JSON POST |
| Exa | 需要 | JSON POST + `x-api-key` |
| 自定义 JSON API | 可选 | GET 模板，支持 `{query}`、`{count}`，解析常见 `results/web.results/data` |

默认不开启联网搜索，避免应用在用户不知情时把问题交给另一个服务。免费预设不等于私密、稳定或无限额。

### 2.3 上下文建议值

| 项目 | 兼容档 | 推荐档 | 自定义范围 |
| --- | ---: | ---: | ---: |
| 活动对话字符 | 49,152 | 131,072 | 32,768–1,048,576 |
| 活动消息 | 32 | 64 | 16–256 |
| 单条正文字符 | 24,576 | 49,152 | 8,192–262,144 |
| 思考字符 | 8,192 | 16,384 | 4,096–131,072 |
| RMS 保存消息 | 24 | 64 | 16–256 |
| 单次请求上下文字符 | 49,152 | 96,000 | 16,384–1,048,576 |
| 搜索来源字符 | 4,000 | 6,000 | 1,000–32,000 |
| 搜索结果 | 3 | 5 | 1–10 |

请求同时受“最近消息数”和“请求上下文字符”约束。推荐值是起点，不声称适合所有型号；自定义模式需要用户主动选择，保存时再次显示风险提示。

### 2.4 图片建议值

| 模式 | 输入压缩大小 | 输入/预览像素 | 返回图片 |
| --- | ---: | ---: | ---: |
| 兼容 | 96 KiB | 65,536 | 256 KiB |
| 高性能 | 512 KiB | 1,048,576 | 1 MiB |
| 自定义绝对上限 | 4 MiB | 4,194,304 | 8 MiB |

判断：

- S60 高端机、Symbian^3 和后期高端索爱机可以大幅放宽压缩文件限制；真正风险来自解码后的像素缓冲和缩放临时数组，而不是 JPEG 文件本身。
- 因厂商 JVM 堆大小、图片解码器和碎片化差异很大，不按机型字符串自动解锁。用户显式选择高性能档更可预测。
- 所有模式在解码前计算压缩字节、像素缓冲和缩放缓冲的保留量；不足时仅跳过预览，不影响纯文字使用。
- 已知 Content-Length 的返回图片直接读入单一目标数组，减少一次整图复制。

## 3. 网关方案

v0.4 网关增加：

`GET /v1/search?q={query}&count={count}`

它与聊天和模型目录使用同一个设备令牌，统一返回：

```json
{
  "results": [
    {"title": "...", "url": "...", "snippet": "..."}
  ]
}
```

网关的 `SEARCH_PROVIDER` 支持 `free`、`searxng`、`brave`、`tavily`、`exa`、`custom`。手机端选择“自定义 JSON API”，搜索端点填写网关地址，Key 填设备令牌即可。默认 `free` 不需要搜索密钥；付费预设使用仅保存在电脑上的 `UPSTREAM_SEARCH_API_KEY`。

## 5. 验收清单

- 新建三个对话后可任意切换，重启后标题、顺序和活动对话正确。
- 从 v0.3 覆盖升级后，每个非空档案历史恰好迁移一次，旧库保留。
- 损坏对话主索引时可从副本恢复；损坏单条消息时不会把错误数据当成有效文本。
- 编辑中间用户消息后，旧后续分支消失，新请求只携带新分支。
- 搜索失败时保留编辑内容；搜索成功时气泡显示来源数，重启后来源仍存在。
- 免费、SearXNG、Brave、Tavily、Exa、自定义和网关结果各至少完成一次夹具解析。
- 兼容档在 W995 上不比 v0.3 更容易 OOM。
- 高性能档分别验证 256 KiB、512 KiB 和 1 MP 图片；内存不足时显示可恢复错误。
- 自定义上下文逐档增加，记录首个明显卡顿、网络失败和 OOM 的阈值，不把单台设备结果硬编码为全局默认。
